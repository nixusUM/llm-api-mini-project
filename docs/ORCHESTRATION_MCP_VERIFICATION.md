# Orchestration MCP — анализ задачи и кейсы проверки

## Пошаговая демонстрация (как показать, что задание выполнено)

1. **Запуск**
   - В терминале: `cd <проект>`, `source .venv/bin/activate`, `python web.py`.
   - В браузере открыть `http://127.0.0.1:5051` (порт смотреть в выводе).

2. **Несколько MCP-серверов**
   - Справа открыть вкладку **Orchestration**.
   - В блоке **Registered MCP servers** показать список: есть **local** и **public** (если установлены Node/npx).

3. **Маршрутизация**
   - В той же вкладке посмотреть таблицу **Tool → server routing**: у части инструментов сервер **local**, у части (например `echo`, `add`) — **public**. Подчеркнуть, что запросы идут на нужный сервер по имени инструмента.

4. **Длинный флоу с разными серверами**
   - Слева: в поле **Orchestration query** ввести `qui`, **Orchestration limit** — `3`, **Output file** — `orchestration_summary.txt`.
   - Нажать **Run orchestration flow (local + public MCP)**.
   - Справа во вкладке **Orchestration** в **Orchestration flow result** показать JSON: 4 шага по порядку — `search_data` (local) → `summarize_data` (local) → `echo` (public) → `save_to_file` (local), у каждого указаны `server_id` и `tool_name`.

5. **Результат флоу — агенту**
   - После шага 4 в поле сообщения (центр страницы) автоматически подставится текст с summary флоу и инструкцией агенту.
   - Нажать **Send** — агент ответит по этим данным (краткие выводы и т.п.). Так показывается, что длинный флоу завершается и результат передаётся агенту.

6. **Дополнительно: другие MCP-инструменты**
   - Слева раскрыть блок **Weather, rates, quote**.
   - Ввести город (например Berlin), нажать **Get weather** — ниже появится погода; она же подставится в промпт — можно отправить агенту.
   - **Get exchange rate**: From `USD`, To `EUR` → **Get exchange rate** — показывается курс.
   - **Get random quote** — случайная цитата и подстановка в промпт для агента.

7. **Проверка файла после флоу**
   - В терминале: `cat data/pipeline_outputs/orchestration_summary.txt` — в файле должен быть текст summary из шага флоу.

**Итог:** показаны регистрация нескольких серверов, маршрутизация по инструментам, длинный флоу с вызовами с local и public, порядок вызовов в результате и передача результата агенту через промпт.

---

## Соответствие требованиям

| Требование | Реализация |
|------------|------------|
| **Несколько MCP-серверов** | В `mcp_orchestrator.py`: `SERVERS` — `local` (локальный Python-сервер) и `public` (npx `@modelcontextprotocol/server-everything`). |
| **Агент выбирает нужный инструмент** | Оркестратор в коде задаёт последовательность инструментов в длинном флоу; маршрутизация по имени инструмента через `get_tool_to_server_map()` и вызов через соответствующий сервер. |
| **Корректная маршрутизация** | Каждый вызов идёт через `call_mcp_tool_sync(..., cli_args)` с `cli_args` нужного сервера (local/public). |
| **Длинный флоу взаимодействия** | `run_long_flow()`: 4 шага — search_data → summarize_data → echo → save_to_file, с передачей данных между шагами. |
| **Сценарий с инструментами с разных серверов** | Флоу использует local (шаги 1, 2, 4) и public (шаг 3 — echo). |
| **Корректность выбора и порядка вызовов** | Порядок фиксирован; в UI и в JSON результата видно `server_id` и `tool_name` по шагам — можно проверить выбор и порядок. |

## Кейсы проверки (как проверить)

### Подготовка

- Активировать venv: `source .venv/bin/activate`
- Запустить веб: `python web.py`
- Открыть в браузере: `http://127.0.0.1:5051` (или порт из вывода)
- Для полной проверки (включая шаг `echo` на public) нужны установленные **Node.js** и **npx**

---

### Кейс 1: Регистрация нескольких MCP-серверов

**Цель:** убедиться, что зарегистрированы минимум два сервера и они отображаются в UI.

**Шаги:**

1. Открыть правую панель, перейти на вкладку **Orchestration**.
2. В блоке **Registered MCP servers** посмотреть список.

**Ожидание:**

- В списке есть минимум два пункта: **local** и **public** (если public недоступен, может быть только local).

**Дополнительно (CLI):**

```bash
python -c "
from mcp_orchestrator import SERVERS
print('Servers:', list(SERVERS.keys()))
# Ожидается: ['local', 'public']
"
```

---

### Кейс 2: Маршрутизация инструментов (tool → server)

**Цель:** проверить, что каждый инструмент привязан к правильному серверу и запросы маршрутизируются корректно.

**Шаги:**

1. Вкладка **Orchestration**.
2. Блок **Tool → server routing** — таблица «Tool» / «Server».

**Ожидание:**

- Есть инструменты от **local**: например `ping`, `sum_two_numbers`, `search_data`, `summarize_data`, `save_to_file`, `get_todo_from_mock_api`, инструменты планировщика и т.д. — в колонке Server указано **local**.
- Если public доступен: есть инструменты от **public** (например `echo`, `add`, …) — в колонке Server указано **public**.

**Проверка порядка и выбора (для флоу):**

- `search_data` → **local**
- `summarize_data` → **local**
- `echo` → **public**
- `save_to_file` → **local**

---

### Кейс 3: Длинный флоу — использование инструментов с разных серверов

**Цель:** выполнить сценарий, в котором в одном флоу вызываются инструменты и с local, и с public.

**Шаги:**

1. В левой панели найти блок с полями оркестрации:
   - **Orchestration query** — ввести, например: `qui`
   - **Orchestration limit** — например: `3`
   - **Output file** — например: `orchestration_summary.txt`
2. Нажать кнопку **Run orchestration flow (local + public MCP)**.
3. Открыть вкладку **Orchestration** и смотреть блок **Orchestration flow result**.

**Ожидание:**

- В JSON есть массив **steps** из 4 элементов.
- Шаги по порядку:
  1. `server_id: "local"`, `tool_name: "search_data"`, `ok: true` (при валидном запросе).
  2. `server_id: "local"`, `tool_name: "summarize_data"`, `ok: true`.
  3. `server_id: "public"`, `tool_name: "echo"`, `ok: true` (если npx/public доступен; иначе возможна ошибка).
  4. `server_id: "local"`, `tool_name: "save_to_file"`, `ok: true`.
- В корне результата `"ok": true`, если все шаги прошли успешно.

Тем самым проверяется и **сценарий с инструментами с разных серверов**, и **корректность выбора и порядка вызовов**.

---

### Кейс 4: Корректность порядка вызовов и передачи данных

**Цель:** убедиться, что порядок вызовов правильный и выход одного шага используется в следующем.

**Шаги:**

1. Выполнить флоу, как в кейсе 3 (query `qui`, limit 3).
2. В **Orchestration flow result** посмотреть по шагам:
   - Шаг 1: `search_data` — в `text`/структуре должны быть данные поиска (например, посты с «qui»).
   - Шаг 2: `summarize_data` — в `text` должен быть краткий summary.
   - Шаг 3: `echo` — в `text` должен быть тот же текст, что и summary (echo возвращает переданное сообщение).
   - Шаг 4: `save_to_file` — успешное сохранение.

3. Проверить файл на диске:

```bash
cat data/pipeline_outputs/orchestration_summary.txt
```

**Ожидание:**

- Содержимое файла совпадает с summary из шага 2 (и с сообщением, вернувшимся в шаге echo). Порядок вызовов и передача данных между шагами корректны.

---

### Кейс 5: Только локальный сервер (без Node/npx)

**Цель:** проверить поведение, когда публичный MCP недоступен (например, нет npx).

**Шаги:**

1. Убедиться, что npx не в PATH или что публичный сервер не запускается (по желанию можно временно изменить конфиг).
2. Открыть вкладку **Orchestration** — в **Registered MCP servers** может быть только **local**; в **Tool → server routing** — только инструменты local.
3. Запустить **Run orchestration flow** (как в кейсе 3).

**Ожидание:**

- Шаги 1, 2, 4 (local) выполняются с `ok: true`.
- Шаг 3 (echo на public) может быть с ошибкой (например, таймаут или «command not found»). В результате флоу `"ok": false`, но видно, что маршрутизация по серверам работает: local-инструменты выполнены, public — помечен как failed.

---

### Кейс 6: Разные запросы и лимиты

**Цель:** убедиться, что оркестратор передаёт параметры в инструменты и результат зависит от ввода.

**Шаги:**

1. Запустить флоу с **Orchestration query** = `qui`, **Orchestration limit** = `2`.
2. Запомнить или скопировать краткий summary из результата (шаг 2 или 3).
3. Запустить ещё раз с query = `eum` (или другим словом из mock API), limit = `2`.
4. Сравнить результаты.

**Ожидание:**

- Разные запросы дают разный состав данных в шаге 1 и разный текст summary в шагах 2–3; файл в шаге 4 перезаписывается новым содержимым. Параметры маршрутизируются в нужный сервер и инструмент.

---

### Кейс 7: Snapshot — инструменты обоих серверов (опционально)

**Цель:** убедиться, что в приложении видны инструменты и local, и public (если оба подключены).

**Шаги:**

1. В левой панели нажать **Test MCP connection** (локальный сервер).
2. Нажать **Test Public MCP** (публичный сервер).
3. Открыть вкладку **Snapshot** в правой панели.

**Ожидание:**

- В Snapshot отображаются блоки **MCP tools** (local) и **Public MCP tools** (public) с перечнем инструментов. Это подтверждает, что оба сервера доступны и список инструментов строится — консистентно с таблицей **Tool → server routing** во вкладке Orchestration.

## Краткий чек-лист результата

- [ ] Зарегистрированы минимум два MCP-сервера (local, public).
- [ ] В UI видна таблица маршрутизации Tool → Server для инструментов обоих серверов.
- [ ] Запуск **Run orchestration flow** выполняет длинный флоу из 4 шагов.
- [ ] В флоу используются инструменты и с **local** (search_data, summarize_data, save_to_file), и с **public** (echo).
- [ ] Порядок вызовов: search_data → summarize_data → echo → save_to_file; данные между шагами передаются (summary уходит в echo и в save_to_file).
- [ ] В результате флоу видно `server_id` и `tool_name` по каждому шагу; при успехе создаётся файл в `data/pipeline_outputs/`.

После прохождения этих кейсов считаем выполненным: **длинный флоу взаимодействия с несколькими MCP-серверами и инструментами** с проверкой регистрации серверов, маршрутизации запросов и корректности выбора и порядка вызовов.
